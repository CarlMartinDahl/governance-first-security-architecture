# Governance-First Security Architecture
## Log Integrity And Tamper-Evidence Policy
**Version:** 0.1 — Initial Release
**Status:** Active
**Classification:** Governance Policy

---

## 1. Purpose

This policy governs the integrity, immutability, and tamper-evidence of audit and operational logs. Logs are among the first targets of an attacker seeking to conceal their activity. An organisation whose logs can be modified, deleted, or disabled by an attacker — or by a compromised system — loses the ability to reconstruct what happened, scope the incident, and meet legal or regulatory obligations.

Log integrity is a governance decision: it requires explicit choices about where logs go, who can access them, and what triggers an alert when logs are missing or modified.

---

## 2. Scope

Applies to all logs generated by systems within scope of this architecture: authentication events, access events, system events, network flow logs, application logs, administrative actions, and security tool outputs. Complements the Audit And Accountability document, which defines what must be logged. This document defines how logs must be protected.

---

## 3. Core Governance Principle

> **A log that can be deleted by an attacker is not a log — it is a liability. Log integrity must be enforced architecturally, not by policy alone. The absence of expected logs is itself an alert condition.**

---

## 4. Credential And Token Logging Prohibition

Authentication credentials and session tokens are the primary target in token replay and credential theft attacks. A log that contains credentials in cleartext is itself an attack surface — read access to the log becomes equivalent to write access to any system the credential governs.

The following rules are absolute and may not be overridden by operational convenience or debugging requirements:

- **Authentication tokens, bearer tokens, API keys, session cookies, and MFA codes must never be written to any log in cleartext.** This applies to all log destinations including gateway logs, application logs, debugging output, and diagnostic traces.
- **Request headers containing authentication material must be masked or redacted before logging.** The log record may retain the header name but must replace the value with a fixed redaction marker (e.g. `[REDACTED]`) or a non-reversible hash.
- **Log pipelines that receive raw request data must apply credential scrubbing before writing to any persistent store.** Scrubbing must occur at ingestion, not at query time.
- **Gateway and API proxy configurations must be validated against this requirement as part of every deployment gate.** A deployment that logs credentials in cleartext must be blocked, not flagged for later remediation.
- **Incident response tooling and forensic capture processes must apply the same scrubbing rules.** Forensic preservation does not override this prohibition — token values are never preserved in forensic logs; only token identifiers and metadata are retained.

Compliance with this section must be verified by automated configuration scanning as part of the deployment pipeline. Manual review alone is not sufficient.

## 5. Log Forwarding Requirements

All logs must be forwarded to a centralised log management system that is:

- **Separate** from the systems generating the logs — a compromised system must not have write or delete access to its own log destination
- **Write-once or append-only** for the forwarding account — the account used to ship logs must not have the ability to modify or delete records already written
- **Accessible only to named roles** — log access follows least-privilege; developers and operations staff do not have access to security logs unless their role requires it
- **Geographically or logically separated** from production infrastructure to survive a production environment compromise

---

## 6. Immutability Controls

| Control | Requirement |
|---|---|
| Write-once storage | Log destination must be configured as write-once (WORM) or append-only for the log ingestion account |
| Deletion protection | Log records must not be deletable within their retention period except by a named Log Governance role through a documented exception process |
| Forwarding lag alert | If log forwarding from any system stops for more than 15 minutes, an alert is generated — silence is treated as a signal |
| Hash chaining (recommended) | Where technology supports it, log records should include a hash of the previous record to enable tamper detection |
| Out-of-band integrity check | At minimum weekly, log volume and record counts are compared against expected baselines; deviations trigger investigation |

---

## 7. Retention Requirements

| Log Category | Minimum Retention | Extended Retention Trigger |
|---|---|---|
| Authentication and access logs | 1 year | Active incident: retain until investigation closed |
| Administrative action logs | 2 years | Any governance exception event |
| Security tool and alert logs | 1 year | Active incident |
| Network flow logs | 90 days | Active incident |
| Application error and exception logs | 90 days | Post-incident forensic review |

Retention periods may be extended by regulatory obligation. They may not be shortened without documented approval from the Log Governance role.

---

## 8. Log Access Control

- Log access is read-only for all roles except Log Governance
- Log Governance is a named role; no service account holds this role
- All access to logs — including read access — is itself logged in a separate audit trail
- Bulk export of log data requires approval from the Log Governance role and is logged as a high-severity event
- No production system has credentials that allow modification or deletion of log records

---

## 9. Alert On Log Absence

The following conditions generate alerts and are treated as security events until proven otherwise:

- Log forwarding from any monitored system stops for more than 15 minutes
- Log volume from a system drops more than 50% below its rolling 7-day baseline without a corresponding maintenance window
- Log records are found to have been deleted or modified within their retention period
- The log forwarding account authenticates from an unexpected source
- Any modification to log retention policy, log forwarding configuration, or log access control

---

## 10. Forensic Preservation

When an incident is declared:

1. Logs from all systems in scope are immediately exported to a forensic-hold storage location with deletion protection
2. Forensic hold is independent of the normal log management system
3. Forensic hold records are not modified, deduplicated, or normalised — they are preserved as received
4. Chain of custody for forensic log exports is documented from the moment of collection
5. Forensic holds are maintained until legal hold requirements are confirmed resolved

---

## 11. Regulatory And Legal Considerations

Log integrity directly affects the organisation's ability to:
- Demonstrate compliance with GDPR Article 32 (technical and organisational security measures)
- Respond to data subject access requests and breach notifications
- Meet NIS2, ISO 27001, and sector-specific audit requirements
- Produce evidence in legal proceedings

The Log Governance role is responsible for ensuring log practices meet current regulatory requirements and liaising with legal counsel when log evidence may be required.
